# Этика, приватность и происхождение данных

Статус: **политика проектирования и план проверки**. API, UI, RAG, реальные POI и внешние провайдеры ещё не проверены. Формулировки «планируем» и «должно» описывают намерение; утверждать, что данные нигде не сохраняются, сейчас нельзя. Все продуктовые пункты ниже — **NOT RUN**.

## Какие данные и зачем

Для подбора нужны запрос, приблизительная локация или введённый ориентир, время, режим передвижения, язык и явно выбранный профиль. Флаг доступности и текст пользователя могут раскрывать чувствительные обстоятельства. Не нужны имя, контакты, ИИН, точный домашний адрес, история перемещений или профиль между запросами. Цель — ответить на текущий городской запрос; новые цели требуют отдельного решения и понятного объяснения пользователю.

Целевое поведение Frontend: запрашивать GPS только по нажатию, разрешать ввод ориентира и выбор на карте, округлять координаты до трёх знаков **до отправки**. Это примерно масштаб квартала, а не гарантия точности 100 м или анонимности. Ориентир, IP-адрес и текст также могут помочь установить место. Отказ от GPS не должен блокировать ручной ввод.

## Границы системы и внешняя передача

| Поток | Предполагаемые данные | Что требуется проверить |
|---|---|---|
| Браузер → Backend | Запрос, округлённая location, профиль и время | Схема POST, округление до отправки, отсутствие лишних полей |
| Backend → LLM | Маскированный текст, контекст и кандидаты | Фактический payload; нужны ли координаты модели; настройки провайдера, retention, трассировка и договорённости |
| Backend → embedding | Текст поиска или описания POI | Не уходит ли сырой PII; где хранится embedding и исходный текст |
| Поиск ориентира → геокодер | Название места, возможно область поиска | Провайдер, запросы, кэш и условия хранения |
| Браузер → карта / тайлы | IP, запрошенные тайлы, потенциально referer | Тайлы раскрывают область просмотра; округление POST не предотвращает эту передачу |
| API → логи / аналитика / traces | Планируется только техническая телеметрия | Payload, query, координаты и profile могут попасть в access logs, exception traces и мониторинг без явного контроля |

Внешние LLM, embedding, геокодер и картографический провайдер могут получать данные. Отсутствие собственной БД не означает отсутствия хранения у этих сторон, в прокси, APM, browser cache или резервных копиях. Провайдер и его настройки ещё не выбраны / не проверены QA. Перед публичным демо инвентаризировать потоки и обновить понятное уведомление по фактической конфигурации; не обещать «ничего не хранится upstream».

## Целевые меры и evidence

| Намерение | Проверка | Сейчас |
|---|---|---|
| Не сохранять точные координаты и сырые запросы в системе приложения | Синтетические запросы с различимыми координатами; поиск в Backend, proxy, analytics, traces и crash reports; проверка конфигурации retention | NOT RUN |
| Не хранить локацию в браузере между запросами | Проверить localStorage, sessionStorage, IndexedDB, service worker, URL/history и кэш; язык/фильтры не должны включать координаты | NOT RUN |
| Маскировать контакты до передачи модели | Перехватить provider-adapter payload; отдельно проверить логи ошибок и embedding, а не только финальный ответ | NOT RUN |
| Показывать использованные данные | Сверить `used_context` и UI с фактическим запросом, языком, радиусом и фильтрами | NOT RUN |
| Минимизировать телеметрию | Оставить request_id, latency и агрегатные счётчики, проверить отсутствие содержимого запроса | NOT RUN |
| Контролировать внешние сервисы | Документировать провайдеров, endpoint, передаваемые поля и применённые настройки; проверить сеть | NOT RUN |

Для QA используются только синтетические данные: `qa.person@example.com`, заведомо тестовые телефон и ИИН с явной надписью «СИНТЕТИЧЕСКИЙ ТЕСТ». Это не данные реального человека. Не переносить реальные пользовательские запросы, токены, скриншоты с контактами или payload провайдера в открытые golden set и отчёты. Наблюдения сохранять обезличенными; редактура evidence не заменяет исправления утечки в продукте.

## Честность рекомендаций

- Неизвестные часы — `unknown` с заметкой; ни наличие названия, ни LLM-сводка не подтверждают открытость. Учитывать прибытие и длительность визита, праздники, закрытия и свежесть источника.
- Не обещать доступность, тишину, розетки, детскую пригодность, свободные столы или безопасность района без проверяемых сведений. `wheelchair = null` не равен `yes`; доступный вход не гарантирует доступный маршрут.
- Для туриста перед вылетом отделять прогулочный бюджет от возврата, контроля, посадки и запаса. Расчёт по прямой не даёт гарантии успеть на рейс.
- Не выдавать категории/популярность за объективное качество. Без подтверждённого рейтинга показывать `null`; сгенерированная «оценка» недопустима.
- Проверять покрытие RU / KK / EN и районов. Неравномерная полнота данных может давать неравные рекомендации. Будущие рекламные/партнёрские размещения должны быть обозначены.

## Происхождение и обновление

Планируются OSM, Wikipedia/Wikidata и сайты мест с полями источника, URL и даты обновления. Согласованный командой целевой режим для OSM — сохранить атрибуцию **© OpenStreetMap contributors** и учитывать ODbL. Перед распространением датасета Data & RAG должны проверить фактические лицензии, условия API, производные базы и необходимые уведомления по [официальной странице OSM](https://www.openstreetmap.org/copyright). Этот документ не подтверждает юридическую проверку всех источников или право на сторонние рейтинги, фотографии и отзывы.

`description_source = llm_generated` обозначает сгенерированное описание; оно не является независимым проверенным источником. `source = generated` у идеи также не разрешает выдумывать ID или свойства места. При конфликте источников сохранять provenance и неопределённость, а не выбирать удобный факт без объяснения. Устаревшее или закрытое место помечать, исключать из активной выдачи при подтверждённом закрытии, исправлять в следующей версии данных с датой и источником изменения.

## Prompt injection и безопасное отображение

Пользовательский запрос и описания POI — недоверенные данные. Целевые меры: отделить инструкции от контекста, ограничить выбор известными кандидатами, проверить структуру и ID, безопасно отобразить текст и ссылки, ограничить исходящие действия. Сам по себе тег `<untrusted_data>` не доказывает устойчивость модели. Извлечение системного промпта, выполнение внешнего HTTP-запроса и исполнение HTML/JS проверяются отдельно.

Прямые атаки golden set проверяют вывод на синтетический canary и опасные строки. Они не доказывают отсутствие иных утечек. **Косвенная атака через POI пока PENDING:** нужна вредоносная тестовая `description`, реально попавшая в retrieval, и наблюдение ответа/сети. Переупаковка той же атаки в пользовательский `query` не является такой проверкой.

## Условия заявления о приватности

До публичного заявления нужны проверенный UI с округлением, аудит логов/хранилищ, перехват payload к каждому внешнему провайдеру, настройки хранения и утверждённый текст уведомления. В демо до этого говорить: «Мы спроектировали минимизацию данных; реализация и внешние потоки проверяются». Не использовать изначальную фразу «ничего не храним» как доказанный факт.
