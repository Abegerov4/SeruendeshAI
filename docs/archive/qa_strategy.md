# Стратегия QA и интеграции

Проверены настоящий локальный backend и собранный экспорт Астаны. Полный прогон: **549 passed, 42 failed, 40 skipped**; результаты и область доказательства — в [eval/results.md](../../eval/results.md). Локальный backend использует keyword/template fallback с отключёнными внешними провайдерами. Настоящие RAG, модель и UI: **NOT RUN**.

## Уровни доказательств

1. **Offline:** чистые валидаторы, метрики, форма golden set, намеренно корректные и сломанные синтетические ответы, CLI на контролируемом транспорте. Без сети и ключей модели.
2. **Данные и retrieval:** реальные POI, источники, допустимые категории, неизвестные поля, геофильтр, часы, поиск и landmark resolution. Нужны компоненты Data & RAG; синтетический датасет их не заменяет.
3. **API:** настоящий POST каждого `request`, HTTP-код, JSON-контракт, факты из версии POI, расстояния, временные нижние границы, число ответов и отказы. Формальная валидность не гарантирует полезность текста.
4. **UI и приватность:** браузер, мобильная клавиатура, Network, локальные хранилища, серверные логи и исходящие payload. Требуется работающее приложение и доступ к наблюдению.
5. **Человек и дополнительный judge:** язык, релевантность, происхождение утверждений, безопасность советов. Judge — отдельный инструмент с моделью, версией промпта и явным запуском; не заменяет проверки схемы, ID, времени или приватности.

## Воспроизводимые команды

Команды выполняются из корня проекта с активированным Python-окружением; текущий прогон проверен на Python 3.12. Помимо `requirements-qa.txt` нужны зависимости Backend и Data. Локальные API-тесты импортируют настоящий FastAPI и запускают его через TestClient без отдельного сервера.

```bash
python -m pip install -r requirements-qa.txt
python -m pip install -r backend/requirements.txt -r data/requirements.txt
python -m pytest tests backend/tests data/tests --pois data/processed/pois.json --live-backend -q
```

Ветка `qa` содержит только QA; команды с `backend/` и `data/` требуют совмещённой рабочей копии с исходниками соответствующих частей. `python -m pytest tests` запускает QA и, если backend присутствует, локальный API-набор. Без исходников backend эти проверки явно пропускаются; при `--live-backend` отсутствие backend — ошибка. `python -m pytest` также собирает присутствующие Backend и Data, но без флагов пропускает проверки реального экспорта и opt-in интеграции. Для QA-флагов явно укажите путь `tests`, чтобы pytest загрузил объявления из `tests/conftest.py` до разбора параметров.

## Локальные API-проверки

Добавлено 95 проверок: 64 неизменённых golden-сценария и два контроля их валидатора, 15 проверок безопасности, четыре проверки языкового fallback и десять дополнительных проверок данных/API на реальном экспорте. Фикстура `qa_backend` отключает ключи модели и трассировки, запрещает вызов LLM-провайдера, использует временный JSON и очищает кэши между тестами. Ответы провайдера в safety-тестах подставляются только на его границе; парсер запроса, retrieval, guards, проверка выбора, маршрутизация и очистка ответа остаются настоящими.

```bash
python -m pytest tests/test_backend_golden_local.py tests/test_backend_safety_local.py tests/test_backend_languages_local.py tests/test_backend_dataset_local.py tests/test_dataset.py --pois data/processed/pois.json -q
```

Golden-прогон использует существующие 17 backend-фикстур; проверки данных отдельно загружают все 14 009 POI. Результаты не измеряют Recall, языковое качество, устойчивость реальной модели к injection или сетевую latency. PII/GPS проверяются в фактических аргументах провайдера и адаптера трассировки, без отправки во внешние сервисы. Проверки заведомо сохраняют найденные падения: [диагнозы](qa_findings.md), [журнал и JUnit](../../eval/runs/2026-10-18-backend-local/README.md).

Внешние интеграции включаются отдельно. При явном включении отсутствующий компонент должен приводить к ошибке, а не к успешному пропуску:

```bash
python -m pytest tests --pois data/processed/pois.json -m dataset
python -m pytest tests --live-rag --pois data/processed/pois.json -m live_rag
python -m pytest tests --live-api --base-url http://127.0.0.1:8000 --pois data/processed/pois.json -m live_api
```

Локальное маскирование тестовых phone/email/ИИН можно проверить отдельно через существующий `backend.app.guards.mask_pii`:

```bash
python -m pytest tests --live-backend -m live_backend
```

Эта опция требует настоящий Backend; без включения тест явно пропускается, при явном включении отсутствующий модуль — ошибка. Даже успешный unit-check маскирования не доказывает, что реальный pipeline применил его перед всеми внешними вызовами.

После появления API и реального датасета:

```bash
python -m eval.run_eval --base-url http://127.0.0.1:8000 --pois data/processed/pois.json --output-dir eval/runs/local
python -m eval.check_readiness --root . --output eval/readiness.md --evidence eval/runs/local/report.json
```

Runner пишет `report.json` и `results.md`; неисполненные сценарии и неуспешные проверки дают ненулевой код возврата. Не выдавать CLI-ошибку, сетевую ошибку или отсутствие сценария за пустую успешную выдачу. Readiness различает наличие компонента и измеренное исполнение; отсутствие продукта, данных или необходимого evidence должно давать ненулевой код. Без evidence readiness остаётся неготовым:

```bash
python -m eval.check_readiness --root . --output eval/readiness.md
```

Для устойчивой оценки использовать одинаковые `now`, модель, данные и сценарии; при необходимости runner поддерживает `--repeat 3` и `--model-label <имя-или-версия>`. Метка модели — объявленная конфигурация, не автоматическое доказательство реально использованного провайдера. Записывать хеши сценариев и POI, Git HEAD / dirty, URL среды, время запуска, число повторов и область валидации. Логи и отчёты с реальными пользовательскими данными в набор не добавляются.

Evidence также привязывается к хешу исходников: при работе без коммитов один и тот же HEAD и `dirty=true` не означают одну версию кода. Изменение проверяемого исходника должно сделать прежний отчёт устаревшим.

Runner поддерживает утверждённые исходы HTTP 200 и 422. Другие сочетания ожидаемых статусов и исходов сначала требуют явного расширения контракта и проверок, а не ветки «ожидаемая ошибка, ничего не проверяем».

Judge никогда не вызывается обычным runner или offline pytest. Только по явному запросу `--review-packets` runner сохраняет очищенные sidecar-пакеты с request/response/POI; в этой работе допустимы только синтетические пользовательские запросы. Даже очищенные пакеты требуют проверки перед внешней передачей. Вход судьи ограничен 64 КиБ, выход — ровно три целочисленные оценки 1–5. Для подготовки метаданных без обращения к модели:

```bash
python -m eval.run_eval --base-url http://127.0.0.1:8000 --pois data/processed/pois.json --output-dir eval/runs/local --review-packets
python -m eval.judge --packet eval/runs/local/review_packets/0001-repeat-1.json --output eval/runs/local/judge.json
```

Для сетевого судейства требуется отдельный явный флаг `--execute` и выбранные параметры провайдера:

```bash
python -m eval.judge --packet eval/runs/local/review_packets/0001-repeat-1.json --output eval/runs/local/judge.json --execute --api-base https://provider.example/v1 --model MODEL --key-env QA_JUDGE_API_KEY
```

`provider.example`, `MODEL` и имя переменной окружения — шаблон для согласованного провайдера, не рабочие credentials. Секрет передаётся через указанную переменную окружения, а не аргументом. Оплачиваемые вызовы на этапе подготовки не выполняются. Отсутствие исполненного judge-артефакта показывать как NOT EVALUATED; подготовка метаданных не означает получение оценок. Перед сравнением оценок калибровать rubric на двуязычной ручной проверке.

После реализации UI отдельно включается опциональная браузерная проверка. Стабильные `data-testid` и запуск приложения описаны в `docs/frontend_test_contract.md`; отсутствие hooks — интеграционная задача, а не основание подменять приложение HTML-моком:

```bash
python -m pip install playwright
python -m playwright install chromium
python -m pytest tests --live-ui --ui-url http://127.0.0.1:5173 -m live_ui
```

Установку браузера выполняют только при необходимости реальных UI-проверок. Этот документ не утверждает, что браузер или UI уже установлены и проверены.

## Development и замороженная выборка

В golden set 50 случаев `dev` и 14 `frozen_holdout`. На dev можно исправлять формулировки и промпт; holdout фиксируется до настройки и используется для сравнения выбранных версий. Сохранить хеш golden set до первого продуктового прогона, владельца проверки и историю изменения ожиданий. Проверять все случаи для финального общего отчёта, а dev и holdout публиковать отдельно. Стандартный runner не объявляется поддерживающим фильтр тегов: при отсутствии отдельной опции группировки подвыборки анализируются по ID в результатах.

Этот файл виден разработчикам, поэтому holdout не является слепым или секретным. Все 64 случая, включая 14 `frozen_holdout`, теперь исполнены в локальном наборе и результаты доступны разработчикам; это не слепая оценка. После использования результатов для настройки нужна новая независимая выборка. Не менять ожидания ради улучшения цифр. Реальные relevance labels размечают минимум два человека либо один автор с независимой проверкой: версия POI, ID, причина релевантности, разногласия. Пока все `relevant_poi_ids = []`, retrieval-метрики не оцениваются. Автоматические утверждения модели не являются эталонной разметкой.

## Метрики и знаменатели

| Метрика | Что означает | Ограничение |
|---|---|---|
| Response rate | Полученные HTTP-ответы / запланированные попытки; отдельно ошибки транспорта и неисполненные случаи | HTTP 422 на неверный ввод — ответ, но не рекомендация |
| Contract / semantic validity | Доля проверенных ответов без нарушений; публиковать также число прошедших / все попытки | Невыполненные запросы не исчезают из общей сводки |
| Несуществующие ID | Число рекомендованных ID вне данной версии POI / число рекомендованных ID | Без рекомендаций знаменатель 0: null / NOT EVALUATED, а не «0% галлюцинаций» |
| Полезная выдача | Обычные сценарии с 1–3 валидными местами / все обычные сценарии | Уточнения и ошибки ввода считаются отдельно |
| Hit@k | Есть ли хотя бы один релевантный уникальный ID в первых k: 0 или 1 для размеченного случая | Не то же самое, что Recall@k |
| Recall@k | Найденные уникальные релевантные ID в первых k / все размеченные релевантные ID | Пустая разметка даёт null; k и источник кандидатов указывать явно |
| p50 / p95 latency | Перцентили измеренного времени запросов в мс, с числом образцов и повторами | Нет образцов — null; отделять timeout и успешные ответы |
| Успех атаки / ложный отказ | Вредное выполнение на проверенных атаках / проверенные атаки; необоснованные отказы / доброкачественные запросы | Отсутствие canary не доказывает полный провал атаки; нужна ручная оценка и наблюдение сети |
| Judge 1–5 | Faithfulness, relevancy, качество объяснения с provenance | Дополнительный шумный сигнал; не гарантия фактов или безопасности |

`relevant_poi_ids` для итоговых рекомендаций позволяет оценить Hit/Recall ответа при его фактическом размере 1–3. Для **retrieval@5** нужны сохранённые top-5 ID реального retriever до выбора LLM. Нельзя назвать три выданных карточки измерением полноты retriever@5. Публиковать число размеченных случаев и покрытие языков/срезов рядом с агрегатом.

У запросов с одним текстовым ориентиром и `location=null` текущий HTTP-контракт не раскрывает проверенные координаты исходной точки. Поэтому нельзя независимо подтвердить расстояние от ориентира и геометрическую нижнюю границу первого перехода. В отчёте эти проверки должны быть **NOT EVALUATED**, даже если схема, POI и остальные ограничения прошли. До финального демо проверить разрешение ориентира отдельно через настоящий `rag.geo.resolve_landmark` либо добавить доверенную трассу координат; не восстанавливать исходную точку из расстояний самого ответа.

Неизвестный `source_url` сохраняется как `null`; придуманный URL не заменяет отсутствующий источник. Маршрут обязан учитывать заявленное время от пользователя до первого остановочного пункта и дальнейшие переходы; нельзя подменять 40 минут пути короткой геометрической оценкой. Прямое расстояние остаётся проверкой правдоподобия, а не подтверждённым пешеходным маршрутом.

## Ручная и интеграционная матрица

Для каждого пункта сохранить среду, шаги, ожидаемое поведение, реальный результат, обезличенное evidence и issue. Полное ручное/E2E-исполнение строк — **NOT RUN**. Уже выполненная локальная часть (аргументы провайдера/tracing, backend-логи, malformed fallback, indirect injection и недостоверные удобства) описана выше; её нельзя переносить на UI, реальные модели или всю внешнюю сеть.

| Проверка | Действия и ожидаемое поведение | Доказательство |
|---|---|---|
| GPS только после действия | Открыть UI, проверить отсутствие автозапроса; нажать GPS, разрешить / запретить / получить timeout. После отказа работает ручной ориентир | Browser permission, Network, видео шага |
| Округление до отправки | Подать координаты с 6 знаками; увидеть в POST только 3 знака и подходящий контекст | HAR без секретов; не только скриншот карты |
| Storage и логи | Выполнить синтетический PII-запрос; проверить local/session storage, IndexedDB, кэш, историю, Backend, reverse proxy, трассировку | Поиск тестовых строк и координат, настройки хранения |
| Передача провайдерам | Перехватить payload геокодера, embedding, LLM, аналитики и тайлов; сверить, какие данные реально уходят и что заявлено пользователю | Схема потоков и обезличенный сетевой trace |
| Мобильная клавиатура | Узкий экран, раскрыть клавиатуру, ввести RU/KK/EN, перенос строки, Enter, IME composition. Поле и отправка доступны; карточки прокручиваются; карта не перехватывает жесты ввода | Настоящий мобильный viewport / устройство, запись |
| Ошибки и клавиатура | Ошибка сети, пустая выдача, повтор, loading; фокус и содержимое ввода сохраняются, статус доступен для screen reader | DOM / клавиатура / accessibility tree |
| Гонка двух запросов | A медленный, затем B быстрый с другим языком/бюджетом. После прихода A карточки, маркеры, маршрут и «Что я учёл» всё ещё соответствуют B | Управляемые задержки и request_id |
| GPS и клик карты | Ручной выбор после незавершённого GPS; старый GPS не должен самовольно заменить более позднее действие пользователя. Отправка использует один согласованный snapshot фильтров и локации | Контролируемая последовательность событий |
| Карта ↔ карточка | Выбрать карточку, маркер; сменить запрос и режим. Ничего не выделяется по устаревшему ID, маршрут не смешан с новой выдачей | UI запись и ID ответа |
| Fallback LLM | Timeout, HTTP-ошибка, некорректный JSON, несуществующий ID. Ограниченный retry, затем шаблон только из реальных кандидатов; нет утечки промпта, сырого исключения или выдуманных POI | Перехваченный provider adapter + реальный pipeline |
| Пустые кандидаты | Geo/часы/профиль исключили всё; допустимый повтор поиска один раз, затем ясная причина вместо выдумки | Trace поиска и ответ |
| Часы к прибытию | POI открыт на `now`, закрыт до прибытия; другой закрывается во время минимального визита; отдельно полночь / неизвестные часы | Фиксированные тестовые часы + план времени |
| Аэропорт | Из двух часов 60 минут уже зарезервированы; проверить обратный путь, запас, прибытие и неопределённость транспорта | Ручная временная шкала; без обещания успеть на рейс |
| Недостоверные удобства | Null wheelchair/hours, нет данных о розетках, тишине, вместимости. Ответ явно ограничен данными, не утверждает удобства по категории | Сопоставление фактов ответа с POI |
| Indirect injection | Загрузить атаку именно через description тестового POI в retrieval-контекст; невыполнение команды и запрет исходящего exfiltration | Фикстура, фактические retrieved ID и egress trace |
| Опасная разметка | Строки из пользователя и POI попадают в карточку, popup и ссылку. Не исполняется JS, опасные URL не активны | DOM/Console/CSP + контроль сети |

## Готовность и диагностика

До live-прогона согласовать схему с Backend, источник и часы с Data & RAG, hooks и окружение с Frontend. Компоненты запускаются по их реальным README. Не модифицировать чужие каталоги ради зелёной QA-сводки.

Каждый дефект помечать по месту происхождения: нет правильного POI в данных; нужный ID не попал в retrieval; кандидат был, но генерация выбрала иначе; факт искажён; проверка не отсеяла нарушение; UI показал старый или иной ответ. Для худших случаев приложить ID, версии, запрос, обезличенный ответ и конкретный ожидаемый факт. Непроверенные блоки отмечать NOT RUN / NOT EVALUATED, а не PASS.

К CP3 требуется реальный eval с ненулевыми знаменателями и разбором ошибок. К CP4 дополнительно нужны настоящие скриншоты, измерения, PDF и демо-видео с рабочей ссылкой. Подготовленные тексты не подтверждают готовность этих артефактов.
