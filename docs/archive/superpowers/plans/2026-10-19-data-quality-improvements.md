# План улучшения качества данных и проверки RAG

> Для будущего исполнителя: выполнять задачи по одной через TDD и проверку результата. **После аудита пользователь разрешил поэтапную реализацию 19 октября; согласованный проход завершён.** Коммиты и push требуют отдельного указания пользователя.

**Goal:** Повысить подтверждённую полезность существующего набора Астаны и доказать качество поиска на его актуальной версии.

**Architecture:** Сохранить полный набор и provenance. Сначала восстановить проверяемую интеграцию с выбранным runtime, затем улучшать факты, идентичность и доверие. Производные тексты и индексы должны строиться из проверяемых полей, с сохранением неизвестных значений.

**Tech Stack:** Существующие Python pipeline/pytest, JSON, геометрия Shapely; текущие BM25 + Chroma/embeddings после явной настройки индексации. Новые сервисы для первого этапа не требуются.

**Spec:** [аудит](../../../reports/data_audit_2026-10-19.md), [роль 02](../../../../team/02_data_rag.md), [контракт](../../../../team/README.md). База планирования — `big-data` `7a8d116`, датасет SHA-256 `1f815df354ad990d902d76c8676a91013f2d8288a7330e8c3b75a2666db29b74`.

## Ограничения

- Не удалять полный набор ради красивых метрик. Перед пересборкой сохранить исходный снимок; публиковать изменения количества, primary ID и всех source ID.
- Не менять координаты, названия, категории или удобства только по догадке либо названию.
- Неполные часы, рейтинг, доступность, тишина и розетки остаются неизвестными. Не генерировать факты LLM.
- Официальный исходный текст не переписывать под видом авторского; шаблоны, переводы и идеи помечать отдельно.
- Сохранить границу города, атрибуцию, source_records, конфликты и решения карантина.
- Все платные embedding/model-вызовы и обновление внешних источников — отдельный явно выбранный запуск. Docker не должен инициировать их неожиданно.
- В этом документе нет разрешения на реализацию, staging, коммит, push или merge.

## Что нужно решить перед реализацией

1. Какой runtime входит в демо: `backend/` + `rag/` или `ayat_backend/`? Рекомендуется первый, потому что он потребляет основной POI-контракт. Если выбран Ayat, нужен отдельный этап адаптации схемы и индекса.
2. Как трактовать непроверенную категорию при выводе `kid_friendly`? Текущее правило соответствует документу команды; изменение должно быть явным решением о доверии к данным.
3. Какой embedding provider/model и режим построения разрешены? Число объектов и возможные обращения нужно показать до запуска.
4. Метрика внутреннего порога: в роли «Recall@5» описан как попадание ожидаемого места в top-5. Рекомендуется явно назвать это Hit@5 и применять ≥0,7 к доле размеченных запросов с хотя бы одним релевантным ID в top-5. Для истинного Recall@5 отдельно согласовать полноту разметки, macro/micro-усреднение и возможный порог.

| Риск | Будущая проверка / задача |
|---|---|
| Одноимённые филиалы, разные дома, помещения и этажи склеились | Положительные и отрицательные identity-кейсы задачи 3 |

**Файлы:** `rag/tests/test_data.py`, `rag/evaluate.py`, `backend/experiments/retrieval_golden.json`, тесты evaluator и документация запуска. `ayat_backend/tests/*` — только при включении второго runtime в согласованный объём.

**Интерфейсы:** сохранить сигнатуры `search`, `resolve_landmark`, `open_status`, `haversine_m` и `normalize_candidates(...) -> (pois, report)`. OSM-элементы сначала проходят `osm_overpass.parse_elements`, затем нормализацию. Не добавлять несовместимый alias `normalize` только ради теста.

- [x] Зафиксировать выбранный runtime, пути данных/индекса и состав зависимостей.
- [x] Сначала добавить тесты runner: nested request читается; неизвестный размеченный ID отвергается; пустая разметка даёт NOT EVALUATED и не превращается в успешный Recall.
- [x] Перевести старые Data-тесты на текущий вход/API и companion-полигон. Сохранить проверки уникальности, неизвестных полей, дублей и географии, включая 219 записей вне прежнего bbox.
- [x] Проверить 30 существующих retrieval-запросов: идентичность ожидаемых мест, покрытие RU/KK/EN, версии данных. Зафиксировать канонизацию устаревшего primary ID `osm:node/4965336822` в `osm:way/499328514` по сохранённому source_records; не объявлять такое место потерянным и не подменять метки первым ответом поиска.
- [x] До изменения фактов, текстов или идентичности сохранить BM25 baseline: запросы/версия разметки, top-5 ID, ошибки и неисполненные случаи, хеш данных, конфигурация и знаменатели метрик. Если валидной разметки недостаточно, сначала дополнить и проверить её; NOT EVALUATED не заменяет baseline для сравнения before/after.
- [x] Запустить обычный pytest без сокрытия collection errors. Разделить ошибки Data/RAG и настройку Ayat; при выбранном Ayat устранить его конфигурацию отдельной задачей.

**Готово, когда:** согласованный полный набор тестов собирается; любой исключённый runtime исключён явно в документации, а не тихо пропущен. Evaluator честно сообщает недостаточность разметки, пока она не исправлена. Перед переходом к изменениям, влияющим на поиск, имеется проверенная разметка и сохранённый BM25 baseline. Никакая метрика не получена на нулевом знаменателе.

## Задача 5 — управляемый индекс и измерение качества

**Файлы:** `rag/build_index.py`, `rag/retriever.py`, `rag/text.py`, `rag/geo.py`, `backend/app/rag_adapter.py`, `backend/entrypoint.sh`, retrieval-эксперименты и тесты.

- [ ] Согласовать canonical ID/координаты/aliases всех ориентиров между сырым RAG и backend. В текущем проходе исправлен канонический BM25 top-1 Байтерека; полная ревизия resolver не выполнялась. Воспроизвести BM25 top-1 для трёх вариантов Байтерека; решить идентичность и ранжирование до изменения ожидания теста.
- [ ] Сначала добавить тесты отсутствующего, устаревшего и частично построенного индекса: нет ложного `hybrid`, нет неявного внешнего вызова, старый пригодный индекс не повреждается.
- [ ] В manifest связать данные, индексируемые IDs/count, версию построителя текста и provider/model. Для Ayat, если он выбран, нужен отдельный план полноценного преобразования схемы и проверки фактического содержимого.
- [ ] Сделать запуск build явным и контролируемым. Сохранить возможность BM25 и ясную диагностику деградации.
- [ ] После отдельного разрешённого построения сравнить BM25 и hybrid, полный набор и досуговый фильтр на одной проверенной разметке с baseline задачи 1. Измерить Hit@5 как долю размеченных запросов с хотя бы одним релевантным ID в первых пяти. Истинный Recall@5 показывать отдельно, с формулой и выбранным macro/micro-усреднением. Показать ошибки, знаменатели, модель, индекс и хеш данных.

**Готово, когда:** реально проверен заявленный режим поиска; согласованный показатель попадания ожидаемого места в top-5 достигает ≥0,7 на актуальной размеченной выборке — в исходной операциональной формулировке роли это Hit@5. Истинный Recall@5 не получает автоматически тот же порог: его цель и усреднение согласуются отдельно. Старый Hit@5 0,90 на 832 POI не используется как результат нового набора. Недостигнутый согласованный порог остаётся видимым результатом, а не поводом ослабить тесты.
