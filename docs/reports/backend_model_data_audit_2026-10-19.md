## 2. Бэкенд, аккаунты, время и маршруты

### B01. Ограничение запросов обходится поддельным X-Forwarded-For — P1 · R

**Доказательство:** [auth.py](../ayat_backend/app/auth.py), строки 94–102; [main.py](../ayat_backend/app/main.py), 101–110. С одного peer 13-я auth-попытка блокируется при лимите 12, но 15 попыток с разными XFF проходят. Для recommend при лимите 1: разрешён → заблокирован → новый XFF снова разрешён. Это отключает защиту от перебора и расходования ресурсов.

**Причина:** приложение безусловно доверяет заголовку клиента. Словари `_attempts`/`_hits` также не удаляют старые ключи и разделены между процессами: смена XFF создаёт неограниченное число bucket.

**Лучшее решение:** брать IP из middleware, доверяющего только разрешённым proxy; на ingress удалять клиентские forwarding headers. Для публичного сервиса использовать общий атомарный limiter с TTL и дополнительными ограничениями по аккаунту и дорогим операциям. Локальный вариант — ограниченный по размеру map с очисткой.

**Приёмка:** разные XFF недоверенного peer не меняют лимит; просроченные ключи удаляются; несколько workers соблюдают общий лимит.

### B02. Удаление аккаунта оставляет reset-token в SQLite и вызывает HTTP 500 — P2 · R

**Доказательство:** [db.py](../ayat_backend/app/db.py), 47–52, 72–80; [auth.py](../ayat_backend/app/auth.py), 179–184, 245–251. Фактический `PRAGMA foreign_keys=0`. После удаления аккаунта с HTTP 204 остаются три reset-записи; предъявление неиспользованного токена даёт `AttributeError` при обращении к `user.password_hash` и HTTP 500.

**Причина:** `ondelete=CASCADE` объявлен, но SQLite foreign keys не включены; ручное удаление охватывает избранное, а не reset-записи. Confirm не проверяет наличие пользователя.

**Лучшее решение:** включать `PRAGMA foreign_keys=ON` на каждом соединении до использования БД, удалить существующие orphan rows миграцией, удалять связанные данные транзакционно; confirm должен обрабатывать отсутствующего пользователя. Подключение SQLite foreign keys описано в [документации SQLAlchemy](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#foreign-key-support).

**Приёмка:** после удаления нет пользовательских saved/reset rows; любой старый reset-token получает контролируемый 400, без traceback.

### B03. После восстановления доступа остаются действительными другие reset-ссылки — P1 · R

**Доказательство:** [auth.py](../ayat_backend/app/auth.py), 230–234, 245–253. Два заранее созданных действительных reset-token последовательно меняют пароль с HTTP **200/200**. Использованным помечается только предъявленный токен.

**Риск:** ранее полученная злоумышленником ссылка позволяет снова сменить пароль после восстановления доступа владельцем. Отдельно остаётся необходимость атомарного потребления токена при конкурентных confirm.

**Лучшее решение:** в одной транзакции менять пароль, атомарно потреблять токен и отзывать все прочие reset-token пользователя; можно привязать их к версии credentials. Старые session cookie после смены пароля уже инвалидируются через `pv`: это существующее исправное поведение. Общая политика восстановления — в [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

**Приёмка:** после token B ранее выданный token A получает 400; два параллельных confirm одного токена дают ровно один успех.

### B04. Logout удаляет cookie в браузере, но не отзывает сессию — P2 · R

**Доказательство:** [auth.py](../ayat_backend/app/auth.py), 28–29, 105–126, 169–171. Logout → 204, обычный `/auth/me` → 401, повторное предъявление сохранённой cookie → **200**. Максимальный срок токена — 30 дней, если раньше не сменить пароль.

**Лучшее решение:** серверная таблица сессий со случайным ID и признаком отзыва; logout отзывает текущую сессию. Для выхода со всех устройств — отдельная account-wide version. Удаления клиентской cookie недостаточно для отзыва украденной копии, см. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

**Приёмка:** повторный token после logout получает 401; остальные сессии работают согласно явно выбранной политике.

### B05. Избранное принимает неограниченный и нетипизированный snapshot — P2 · R

**Доказательство:** [auth.py](../ayat_backend/app/auth.py), 79–80, 195–211; [db.py](../ayat_backend/app/db.py), 43. Сохраняются `name` из **1 000 000** символов, строка вместо `lat` и объект вместо массива `features`, HTTP 200. Allowlist ограничивает имена полей, а не размеры/типы. Лимит 300 карточек не ограничивает объём БД и ответа.

**Лучшее решение:** типизированная модель snapshot с пределами строк/массивов, валидными координатами/URL и общим пределом байт. Хранить canonical ID и минимальный контролируемый набор данных; по возможности собирать карточку на сервере.

**Приёмка:** неправильные типы → 422, слишком большой запрос → 413/422; нормальная карточка с ID `osm:node/...` сохраняется и восстанавливается.

### B06. Кэши смешивают разное время и возвращают устаревшие часы/дедлайны — P1 · R

**Доказательство:** [service.py](../ayat_backend/app/service.py), 107–125, 384–385; [cache.py](../backend/app/cache.py), 56–62. Ayat-запросы с явным `now=12:00` и `12:14` получают прежний `used_context.now=12:00`. Основной backend создаёт одинаковый ключ для **20:45 и 20:59**, TTL по умолчанию 900 секунд. Открытие, закрытие или изменение достижимости внутри bucket не инвалидируют ответ.

**Лучшее решение:** при явном `now` использовать точное время либо обходить response cache. Кэшировать retrieval отдельно от временной валидации; перед возвратом пересчитывать arrival, часы и deadline. Если кэшировать итоговый ответ — ограничивать TTL ближайшим изменением доступности и версией снимка.

**Приёмка:** явные `now` не схлопываются; после закрытия не выдаётся прежний `open`; leave-by и контекст относятся к текущему запросу.

### B07. «Два часа до вылета» оставляет слишком большой бюджет прогулки — P1 · R · известно ранее

**Доказательство:** [service.py](../ayat_backend/app/service.py), 37, 192–217; [query.py](../ayat_backend/app/query.py), 215–219. В локальном HTTP: запрос в 12:00 с вылетом через 120 минут даёт **90 минут бюджета**, три рекомендации и рассчитанный предельный срок прибытия в аэропорт **13:30**. Дополнительное время регистрации предлагается вычесть вручную в note; фактическая поездка не выполнялась.

**Причина:** единый тип `flight` смешивает departure и airport-arrival; запас 30 минут применяется вместо встроенного расчёта регистрации/контроля. Это подтверждает открытое ограничение исходного отчёта.

**Лучшее решение:** разделить `flight_departure_at` и `airport_arrival_at`, до планирования вычитать configurable pre-departure buffer, дорогу и запас неопределённости. Если вид рейса или смысл времени неизвестен — консервативно ограничить прогулку и запросить нужное уточнение. Конкретный запас должен задаваться проверенной политикой продукта, а не универсальной константой для всех рейсов.

**Приёмка:** «вылет через два часа» и «быть в аэропорту через два часа» дают разные корректные бюджеты; отрицательный остаток приводит к совету ехать в аэропорт, без прогулочного маршрута.

### B08. Ayat допускает визит после закрытия и неточно кэширует проверку расписания — P1 · R/S

**Доказательство:** [hours.py](../ayat_backend/app/hours.py), 112–117; [planner.py](../ayat_backend/app/planner.py), 68–90. `opening_status` возвращает `ok=True`, если до закрытия хотя бы 15 минут, даже при более длинном визите. Planner прибавляет полную исходную длительность. На двух синтетических кафе с закрытием в 12:10 маршрут со старта 11:00 заканчивается **12:32**, второй визит длится 45 минут с 11:47.

**Дополнительная причина:** локальный `open_ok` кэшируется по `(POI, arrival//10)`, без точного arrival. Разные порядки обхода в одном бакете могут получить чужой результат у границы закрытия. Длительность конкретного кандидата внутри текущего вызова planner фиксирована; её отсутствие в ключе само по себе сейчас не является отдельным воспроизведённым дефектом.

**Лучшее решение:** проверять весь интервал `[arrival, departure]`; либо сокращать визит и использовать одну фактическую длительность во всех вычислениях/полях, либо отклонять вариант. Ключ проверки должен включать точное время и длительность, либо проверка должна вычисляться без такого кэша.

**Приёмка:** все остановки заканчиваются до закрытия; порядок перебора маршрутов не влияет на корректность; случаи по обе стороны границы 10-минутного bucket покрыты.

### B09. Матрица маршрута теряет подход от конечного узла графа до POI — P2 · R

**Доказательство:** [planner.py](../ayat_backend/app/planner.py), 28–41; [geo.py](../ayat_backend/app/geo.py), 111–117; рабочая формула [retrieval.py](../ayat_backend/app/retrieval.py), 131–134. Для реального **Turan House**: destination snap **475,7 м**, matrix **7 323,8 м**, reach **7 799,5 м**. Направления получают искусственно разные расстояния.

**Причина:** `from_source` включает подход от начала, но `_matrix` не добавляет подход к конечной точке; retrieval добавляет его отдельно.

**Лучшее решение:** единая функция расчёта leg, учитывающая оба snap и полилинию; ограничить допустимый snap, при превышении выбирать явно обозначенный fallback.

**Приёмка:** расстояние/время origin→POI согласованы между карточкой и route leg; оба подхода присутствуют в расстоянии и геометрии.

### B10. Основной backend проверяет открытие сейчас, но не по прибытии — P1 · R

**Доказательство:** [pipeline.py](../backend/app/pipeline.py), 105–122; [routing.py](../backend/app/routing.py), 38–56. Синтетический музей закрывается в 18:00; запрос в 17:55 даёт `open`, дорогу 16 минут и прибытие **18:11**, когда он уже закрыт. Независимое воспроизведение с кафе: 20:59 + 8 минут при закрытии 21:00 — та же ошибка. Последовательный route не перепроверяет часы.

**Лучшее решение:** сначала вычислять arrival, затем проверять часы и минимальный визит; для каждой остановки маршрута рассчитывать её собственное arrival/departure. Можно переиспользовать единый проверенный модуль B08 вместо двух расходящихся политик.

**Приёмка:** оба примера исключаются или честно обозначаются недоступными; каждый route stop помещается в расписание на момент своего посещения.

### B11. Фото может дать HTTP 500 и неконтролируемую нагрузку до resize — P2 · R/S

**Доказательство:** [main.py](../../backend/app/main.py), 77–80; [vision.py](../backend/app/vision.py), 45–58. Изображение читается целиком до проверки 8 МБ; `convert('RGB')` декодирует полный размер до thumbnail в async endpoint. PNG-заголовок **57 байт** с чрезмерными dimensions вызывает необработанный `DecompressionBombError` и HTTP **500**. Большое изображение для этого воспроизведения не выделялось.

**Лучшее решение:** bounded read до `MAX_BYTES+1`, проверка dimensions/pixel count до decode, обработка bomb/ошибок PIL как 413/422, ограничение параллельных декодирований и вынос CPU-работы из event loop.

**Приёмка:** слишком большое тело не буферизуется целиком; повреждённое/опасное фото возвращает 413/422; нормальные параллельные запросы продолжают обслуживаться.

### B12. MCP-поиск обходит PII-маскирование перед embeddings — P1 для внешних embeddings · R/S

**Доказательство:** [server.py](../backend/mcp_server/server.py), 132–154; [rag_adapter.py](../backend/app/rag_adapter.py), 47–51; [retriever.py](../../rag/retriever.py), 39–49, 84–86; [embeddings.py](../../rag/embeddings.py), 7–11. Spy на retrieval-границе MCP получил исходный query с синтетическим email. При OpenAI dense provider та же строка передаётся в `embeddings.create(input=...)`. Внешней отправки в аудите не было.

**Лучшее решение:** одна sanitization-граница для HTTP/MCP/Telegram до retrieval и model calls, с ограничением длины и тестами provider arguments. Маскирование в HTTP recommendation не защищает соседний MCP tool.

**Приёмка:** синтетические email/телефон/ИИН отсутствуют во входах embedding/LLM spy для каждого транспорта; поиск остаётся работоспособным.

### B13. Telegram хранит location дольше обещанных 30 минут — P2 · S

**Доказательство:** [bot.py](../backend/telegram_bot/bot.py), 30, 58–63, 89–91, 141–149. Удаление просроченной `chat_data.loc` выполняется при следующем обращении к `_saved_location`. Без нового сообщения пользователя координаты остаются до остановки процесса; периодического удаления нет.

**Лучшее решение:** scheduled cleanup независимо от активности пользователя; `/forget` оставляет немедленное удаление. Не обещать более короткую retention, чем обеспечивает код.

**Приёмка:** после TTL координат нет в памяти даже без новых updates; проверка на управляемых часах, без реального 30-минутного ожидания.

## 3. Запуск, CI и доказательства качества

### I01. Локальный UI и стандартный Docker запускают разные продукты/API — P1 · S

**Доказательство:** [run_local_integration.sh](../../scripts/run_local_integration.sh) запускает `ayat_backend.app.main`; [docker-compose.yml](../docker-compose.yml) — основной `backend.app.main` через [backend/Dockerfile](../../backend/Dockerfile). UI вызывает auth/saved/meta и использует расширенные карточки/route legs в [api.js](../../frontend/src/api.js) и [auth.js](../../frontend/src/auth.js); основной сервер не реализует этот контракт. [Ayat README](../ayat_backend/README.md), строка 63, при этом советует root compose.

**Лучшее решение:** явно выбрать поддерживаемый runtime UI и дать ему однозначные run/compose/health-команды. Для функций основного сервера оставить отдельный профиль/сервис с документированным контрактом. Немедленное полное переписывание двух backend не требуется: сначала общие детерминированные политики, затем последовательное сближение API.

**Приёмка:** чистый checkout по одной документированной команде открывает текущий UI с регистрацией, рекомендациями и сохранением; OpenAPI contract test проверяет именно обслуживающий его сервер.

### I02. Docker Ayat не копирует quarantine и возвращает исключённые места — P1 · S + R адаптера

**Доказательство:** [Dockerfile](../ayat_backend/Dockerfile), 7–10, копирует только `data/processed`; [store.py](../ayat_backend/app/store.py), 23–24, 96–101, ищет `data/quarantine.json` и при отсутствии продолжает работу без него. Одинаковый canonical JSON даёт **2 751** recommendation POI с quarantine и **2 756** без файла. Это потеря пяти review-исключений. Сам Docker build не запускался: вывод следует из COPY и воспроизведения loader.

**Лучшее решение:** поставлять единый versioned data bundle с quarantine/overrides; обязательные policy-файлы проверять при startup, их hash включать в manifest. Отсутствие файла не должно молча менять состав рекомендаций.

**Приёмка:** loader в собранном образе даёт тот же hash/ID set и 2 751 POI, что локальный профиль; все пять quarantine ID исключены.

### I03. Образ Ayat не содержит текущий frontend — P1 для единого UI-deploy · S

**Доказательство:** [Dockerfile](../ayat_backend/Dockerfile), 5–10, не собирает и не копирует `frontend/dist`; [.dockerignore](../../.dockerignore) исключает его. [main.py](../ayat_backend/app/main.py), 171–186, регистрирует SPA только при наличии `dist/assets`.

**Лучшее решение:** frontend build stage (`npm ci`, build) с копированием результата в образ либо явно отдельный frontend deployment с правильными API URL, cookies/CORS и собственным smoke-test.

**Приёмка:** для выбранной схемы deployment `/`, assets, deep link и auth API проверяются из свежего образа; отсутствующая сборка диагностируется явно.

### I04. Плановое обновление запускает pipeline по старому namespace — P1 · S

**Доказательство:** [data-refresh.yml](../../.github/workflows/data-refresh.yml), 15–24, работает из `ayat_backend` и вызывает `python -m pipeline.cli`; [cli.py](../ayat_backend/pipeline/cli.py), 13, импортирует `ayat_backend.app.paths`. Из этого cwd `find_spec('ayat_backend')` возвращает **None**; пакет не устанавливается (`tool.uv.package=false`). Локальный `--help` дополнительно остановился раньше на отсутствующем optional `typer`: полноценный прогон CI здесь не заявляется.

**Лучшее решение:** запускать из корня `uv run --project ayat_backend python -m ayat_backend.pipeline.cli ...` либо общий исправленный Makefile; отдельный smoke `--help` после установки pipeline group.

**Приёмка:** workflow на чистом runner импортирует тот же модуль, что локальные команды; import smoke проходит до любых сетевых сборов.

### I05. Даже исправленный refresh обновляет JSONL, который canonical runtime не использует — P1 · S

**Доказательство:** [data-refresh.yml](../../.github/workflows/data-refresh.yml), 20–30; [cli.py](../ayat_backend/pipeline/cli.py), 37–47; [build.py](../ayat_backend/pipeline/build.py), 427–455. Pipeline пишет `pois.jsonl` и legacy manifest; [store.py](../ayat_backend/app/store.py), 96–108, при наличии `pois.json` всегда выбирает canonical JSON. Пересборка legacy embeddings не обновляет canonical view.

**Лучшее решение:** один owner канонического экспорта и одна команда refresh, производящая согласованный runtime bundle; legacy pipeline — явно отдельный эксперимент. PR обновления должен показывать diff активного ID set и используемую версию данных.

**Приёмка:** контролируемая правка/новый POI в исходнике refresh изменяет active canonical manifest и API; обновление не ограничивается неиспользуемым JSONL.

### I06. CI пропускает значительную часть текущих регрессий — P1 · R/S

**Доказательство:** [backend.yml](../.github/workflows/backend.yml), 23–30, запускает `unittest discover -s rag/tests`. Свежий вывод — **7 tests**, тогда как `pytest rag/tests --collect-only -q` собирает **35**. Новые pytest-функции evaluator/text этим шагом не исполняются. В этом workflow также нет `data/tests`, явного реального dataset/RAG opt-in и frontend tests/build; push-фильтр не включает `big-data`. Отдельный Ayat workflow не закрывает эти области.

**Лучшее решение:** единый проверенный pytest entrypoint для Data/RAG/обоих backend/QA с реальным committed snapshot и opt-in local интеграциями; отдельный frontend job; Docker smoke обслуживающего UI runtime. Внешние провайдеры — отдельный явно включаемый ограниченный прогон. Настроить нужные branches/path triggers.

**Приёмка:** CI выполняет все 35 текущих RAG tests, видит data/adapter/API-contract regressions и frontend build; отчёт различает passed/skipped/unexecuted.

### I07. Ayat evaluator не включает визит в проверку бюджета — P1 · R

**Доказательство:** [run_eval.py](../ayat_backend/eval/run_eval.py), 53–56. На валидном по схеме ответе с бюджетом **10 минут**, дорогой **1 минута**, `visit_min=[120,180]`, `visit_suggested_min=120` и без route он возвращает **C1=True, C4=True**. Проверяется только дорога; маршрут получает отдельный допуск +5.

**Лучшее решение:** независимый semantic validator: дорога + фактический визит + требуемое возвращение/буфер; для route — сумма legs и visits с согласованностью карточек, arrival, closing и deadline. Использовать общий смысл ограничений, но независимые вычисления, чтобы тест не повторял дефект реализации.

**Приёмка:** приведённый ответ проваливает C4; fake-route из M02 также проваливается; определения minimum/suggested/range и допусков задокументированы.

### I08. Ayat scenario eval может завершиться успешно при FAIL/HTTP error — P1 · S + R отчётчика

**Доказательство:** [run_eval.py](../ayat_backend/eval/run_eval.py), 167–188, 193–206, 223–224. Ошибочные HTTP собираются с пустым `checks`, FAIL печатается, но `main()` не возвращает ненулевой exit status. Отчётчик для полностью ошибочного HTTP-сценария показывает **0/0** checks. [ayat-backend.yml](../.github/workflows/ayat-backend.yml), 18–21, использует такой запуск как CI step.

**Лучшее решение:** ненулевой код при HTTP/schema/semantic failure, явные counters planned/executed/failed/skipped, HTTP failures не исключать из знаменателя успеха. Разделить «создать отчёт» и «пройти gate».

**Приёмка:** преднамеренный HTTP 500 и C4=False делают CI красным; отчёт показывает failing scenario, не только 0/0.

### I09. Provenance gate не учитывает код сервера текущего UI — P1 · R

**Доказательство:** [run_eval.py](../../eval/run_eval.py), 51–83, хеширует `backend`, `rag`, `frontend`, но не `ayat_backend`; [check_readiness.py](../../eval/check_readiness.py), 19–22, считает основным компонентом `backend/app/main.py`. В изолированном дереве изменение `ayat_backend/app/service.py` оставило `source_fingerprint` неизменным. Сам gate полезен для своего исходного runtime, но не привязывает evidence к текущему UI-серверу.

**Лучшее решение:** runtime-specific provenance: entrypoint, все его исходники/настройки, lockfile, модель/provider, data bundle/overrides/index hashes; проверять соответствие `runtime_id` на API и в report. Для уже dirty-tree изменение Ayat не должно проходить только за счёт неизменного булева `git_dirty`.

**Приёмка:** изменение Ayat planner/service/auth делает прошлое evidence устаревшим; report и health однозначно называют проверенный runtime.

### I10. Health отмечает LLM как ok без доказательства работоспособности — P2 · S

**Доказательство:** [main.py основного сервера](../../backend/app/main.py), 37–48: `ok` зависит от `llm.is_enabled()`; [main.py Ayat](../ayat_backend/app/main.py), 138–148: от создания SDK client. Неверный ключ, отсутствие доступа к выбранной модели или несовместимые параметры этим не обнаруживаются. Ayat warmup best-effort и его результат не определяет readiness.

**Лучшее решение:** разделить liveness, configured, last verified provider probe, degraded mode и readiness выбранного профиля. Локальный template-профиль может быть ready без LLM, но не должен служить доказательством LLM-readiness. Provider probe — редкий, с timeout/TTL и наблюдаемым результатом, а не платный вызов на каждый health request.

**Приёмка:** configured-but-invalid provider не получает verified `llm=ok`; отключённая модель честно отражена; tests различают template-ready и LLM-ready.

### I11. Основной backend может одновременно видеть два поколения данных — P2 · R

**Доказательство:** [rag_adapter.py](../backend/app/rag_adapter.py), 91–113, постоянно кэширует список POI/имён, а [retriever.py](../../rag/retriever.py), 65–67, перечитывает изменившийся файл по mtime/size. В изолированном снимке после добавления второго POI: `new_id_in_search=True`, `new_id_in_all_pois=False`. Триггер — замена файла во время жизни процесса; текущее автоматическое hot-reload deployment не утверждается.

**Лучшее решение:** immutable versioned snapshot и один runtime handle для поиска, ID lookup, карты и aliases. Либо явно обязательный restart с проверкой bundle hash при каждом rollout; не смешивать file-watch retrieval и бессрочный cache.

**Приёмка:** после продвижения версии все endpoints/поиск используют один snapshot ID; новый ID либо доступен везде, либо новая версия не активна нигде.

### I12. Погода, SMTP, внешняя карта и production DB не прошли реальный прогон — P2 · N · известно частично

**Доказательство:** [отчёт интеграции](branch_integration_2026-10-19.md) и [его verification](../../eval/runs/2026-10-19-branch-integration/integration-verification.json): live-погода и SMTP отключены, browser allowlist блокирует map tiles/Google Fonts, аккаунты проверялись на локальной SQLite. Это отсутствие подтверждения, а не утверждение, что сервисы обязательно сломаны. Локальная проверка маркеров не доказывает загрузку внешней подложки.

**Лучшее решение:** отдельный staging-прогон выбранной deploy-конфигурации: weather success/timeout/unknown, reset-email request→получение→confirm на тестовом адресе, HTTPS cookies/proxy, постоянство аккаунта/избранного после restart и работа выбранной production DB, загрузка map tiles с корректной атрибуцией. Проверки внешних отправок выполняются отдельно при настройке соответствующего сервиса; в этом read-only аудите письма не отправлялись.

**Приёмка:** есть фактические результаты для каждой включаемой интеграции, а при недоступности — проверенное понятное поведение UI/API. Локальные ограничения остаются явно видимыми до этого прогона.

## 4. Модель, RAG и фактическая обоснованность

### M01. Правильный POI ID не мешает выдавать выдуманные услуги как данные — P1 · R

**Доказательство:** [generate.py основного backend](../../backend/app/generate.py), 75–89; [generate.py Ayat](../ayat_backend/app/generate.py), 104–118, 184–220; [service.py](../ayat_backend/app/service.py), 438–453. Оба валидатора принимают синтетические тексты про бесплатный Wi-Fi, розетки, вход без ступеней и бесплатную выставку динозавров при отсутствии соответствующих фактов кандидата. Итоговая метка — `source=poi_data`. Ayat-проверка проходит через `service.recommend()` на реальной базе с явно fake generation.

**Причина:** проверяются ID, типы, ссылки, числа и некоторые запрещённые фразы, но не подтверждение утверждений полями источника. Основной backend ещё и доверяет модельному `source`; Ayat ставит `poi_data` для карточки независимо от истинности пояснения. Это доказательство слабости защиты, а не утверждение, что настоящая модель всегда пишет такой текст. Structured Outputs обеспечивают форму ответа, но допускают содержательные ошибки — это прямо отмечает [официальная документация OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).

**Лучшее решение:** модель возвращает выбор ID и допустимые `reason_codes`/ссылки на факты; критичные утверждения о доступности, интернете, цене, часах и событиях формируются сервером из evidence. Свободные идеи помечаются отдельно, provenance назначает сервер. Семантический verifier и human review — дополнительные слои для свободного текста, с отдельной оценкой ошибок.

**Приёмка:** missing/false/conflicting Wi-Fi, wheelchair, fee и event не превращаются в положительные утверждения; подстановка `source=poi_data` не повышает доверие к тексту; каждый фактический reason связан с полем и источником.

### M02. После LLM длительности карточек расходятся с уже рассчитанным маршрутом — P1 · R

**Доказательство:** [generate.py](../ayat_backend/app/generate.py), 193–205; [service.py](../ayat_backend/app/service.py), 246–291, 432–435; [planner.py](../ayat_backend/app/planner.py), 85–90, 127–131. На реальной базе с fake `GenOut`: бюджет **90**, `route.total_min=90`, `fits_budget=true`, дорога **15**, рекомендованные визиты **45 и 67**. Фактическая сумма предложенного плана — **127 минут**. Summary продолжает обещать 75 минут на местах вместо 112.

**Причина:** planner считает маршрут до генерации. Затем `validate()` допускает увеличение до `1.5 × visit_range.max`; `_item()` ограничивает каждую карточку отдельно, а финальные route/hours/deadline не пересчитывает.

**Лучшее решение:** длительности принадлежат planner, LLM пишет объяснение. Для фиксированного route брать времена из `route.timeline`. Если изменение времени всё же разрешено — повторно проверять все legs, визиты, closing и deadline на окончательных значениях до сериализации.

**Приёмка:** сумма длительностей маршрутных карточек, всех legs и возвращения равна `route.total_min`; превышение 90 не может получить `fits_budget=true`. Это проверяется synthetic outputs на границах диапазонов.

### M03. Неполный structured output обрывает fallback Ayat исключением — P1 · R

**Доказательство:** [llm.py](../ayat_backend/app/llm.py), 61–86. Настоящий установленный SDK с локальным `httpx.MockTransport`: HTTP 200, `status=incomplete`, `max_output_tokens`, обрезанный текст `{"summary":` → **pydantic.ValidationError**. Из двух настроенных fake моделей вызвана только одна, fallback не выполнен; реальной сети не было.

**Причина:** SDK разбирает JSON внутри `responses.parse()` до проверки `r.status` на строке 83. Ошибка parsing/validation не входит в обработанные исключения первого вызова. Обещанный шаблонный fallback не достигается.

**Лучшее решение:** отдельно обрабатывать ошибки разбора/валидации SDK, incomplete/refusal и schema-invalid output, продолжать цепочку в пределах общего deadline; после исчерпания возвращать `None`, чтобы включился template. Разобранные времена/дедлайны отдельно проверять на семантическую корректность.

**Приёмка:** mock-transport cases truncated JSON, invalid types, refusal и incomplete не дают HTTP 500; число попыток и суммарный timeout ограничены; финальный режим ответа честно указан.

### M04. Явно названный target пропускает часть жёстких фильтров Ayat — P1 · R на уровне rank()

**Доказательство:** [retrieval.py](../ayat_backend/app/retrieval.py), 179–186 против 212–223. Для synthetic park с `wheelchair=no`, `lit=false`, ночью, при ощущаемых −40 °C и `max_outdoor_min=0`: обычный `rank()` возвращает **0**, с тем же ID в `target_ids` — **1** кандидата.

**Причина:** target-ветка возвращается после hours и kids/adult проверки, до wheelchair, darkness, extreme cold и indoor-only. Последующее предпочтение подтверждённой доступности иногда удаляет такой target, если есть другие кандидаты: поэтому конкретный HTTP-сбой с реальным named destination этим проходом не доказан. Сам обход обязательных условий в `rank()` воспроизведён.

**Лучшее решение:** общий обязательный safety predicate для target и обычных кандидатов. Явное назначение может менять релевантность/радиус, но не игнорировать известную физическую недоступность и ограничения условий; возвращать объяснение отказа.

**Приёмка:** одинаковые target/non-target cases для wheelchair, darkness, cold, indoor-only и kids; дополнительно HTTP-тест с однозначно распознанным назначением и недостатком альтернатив.

### M05. Основной RAG возвращает все пять мест из дополнительного карантина — P1 · R

**Доказательство:** [retriever.py](../../rag/retriever.py), 65–76; [rag_adapter.py](../backend/app/rag_adapter.py), 47–58; исправный сравнительный путь [team_data.py](../ayat_backend/app/team_data.py), 157–185. BM25 по точному имени в радиусе 100 м ставит каждый из пяти canonical ID на **первое место**:

| Canonical ID | Название | Текущая категория |
|---|---|---|
| `osm:way/230409020` | проспект Мәңгілік Ел | restaurant |
| `osm:node/4529345494` | Студия 1337 | attraction |
| `overture:3dda9f68-24a5-4047-a0a0-101ce0a047fc` | Nurlyzhol_vokzaly | bar |
| `overture:5b26880c-5614-4d74-a83d-06d45ed76b94` | ул.Абылай хана 5/2 | cafe |
| `overture:67740c18-c915-4b60-871a-3199c23aebe8` | Divan meiramxanasy | restaurant |

**Причина:** основной RAG использует category/geo-фильтр, но не дополнительный review-файл; форматы review ID `osm:w...`/`ov:...` также требуют явного разрешения в canonical namespace. В Ayat локально эти пять исключений уже работают — это отдельное от I02 расхождение runtime.

**Лучшее решение:** общий read-only слой review/eligibility с однозначным ID mapping для обоих серверов. Сохранять исходные POI как данные/ориентиры, исключать из рекомендаций, а не терять provenance.

**Приёмка:** эти ID отсутствуют в candidate pool обоих серверов и в образе; все source records сохранены; ambiguous alias не выбирает произвольного владельца.

### M06. Основной backend игнорирует конфликт часов и выдаёт high confidence — P2 · R

**Доказательство:** [pipeline.py](../backend/app/pipeline.py), 109–122; [hours.py](../../rag/hours.py), 23–55. У реального «Мизам», `osm:node/4519246690`: primary `Mo-Su 08:00-23:00`, конфликтные версии `24/7` и `Mo-Su 11:00-00:00`. В понедельник 09:00 основной backend даёт **open/high**. В Ayat конфликт часов уже маскируется в [team_data.py](../ayat_backend/app/team_data.py), 95–113.

**Причина:** parser получает одну строку без field conflicts и дат; успешность разбора принимается за достоверность факта.

**Лучшее решение:** разделить syntactic validity и fact confidence. При неразрешённых противоречиях — unknown/спорный статус с evidence; high только по принятой политике актуальности и согласованности источников.

**Приёмка:** конфликтные часы не дают безусловного open/high; свежие непротиворечивые факты сохраняют обычную работу. Отдельные тесты конфликтов и устаревших check dates.

### M07. Для canonical Ayat отсутствует пригодный dense-индекс — P2 · S/N · известно ранее

**Доказательство:** [store.py](../ayat_backend/app/store.py), 96–117; [team_data.py](../ayat_backend/app/team_data.py), 218–219; [embed.py](../ayat_backend/pipeline/embed.py), 18–26. Старый массив имеет форму **(2307, 1024)** и относится к legacy JSONL; активный canonical view содержит **2 751** POI. Loader правильно не подключает несовместимые строки. Текущая legacy embed-команда не строит индекс именно этого view.

**Проблема:** заявленный гибрид не является активным режимом canonical UI; качество семантического поиска на этом составе не измерено. Отключение старого массива — правильная защита, а не ошибка, которую нужно убрать.

**Лучшее решение:** отдельная команда построения canonical index с canonical ID→row, hash ordered ID set, hash документов/eligibility, model/version/dimension и schema version; loader проверяет всё соответствие. Сначала сохранить BM25 baseline и только затем сравнивать dense/hybrid на тех же запросах.

**Приёмка:** индекс покрывает именно активные canonical ID; перестановка/изменение документов делает его stale; hybrid даёт измеренные метрики и допустимую latency, не только `dense_retrieval=true`.

### M08. Остаются retrieval-промахи, а набор качества слишком узок для общего вывода — P2 · R/S

**Доказательство:** [размеченный набор из 35 запросов](../../eval/datasets/astana_retrieval_v2.json), [предыдущий разбор результатов](data_quality_improvements_2026-10-19.md). Свежий BM25-замер этого аудита приведён в разделе 7. Набор до этого уже использовался для подбора aliases и Wi-Fi-нормализации, поэтому не является независимым holdout. Его Hit@5 не измеряет конечный UI-response Hit@3 и полезность текста.

**Открытые случаи:** «триумфальная арка Мангилик Ел», «монумент Казак Ели», «тихо почитать книги». Первые требуют доказанных языковых имён/алиасов; в третьем лексическое совпадение и категория библиотеки не доказывают тишину.

**Лучшее решение:** train/dev и отдельный замороженный holdout; сценарии RU/KK/EN, имена/филиалы, фактические требования, неизвестные часы, дети/доступность и deadline. Отдельно оценивать retrieval Hit/Recall/NDCG, финальный выбор Hit@3, faithfulness и исполнение ограничений. Для пригодности нужны соответствующие метки, а не только nearby/category.

**Приёмка:** три текущих промаха проверены без новых ложных фактов; есть независимые размеченные запросы и доверительные интервалы/числители, а исторические метрики не переносятся на другой runtime или датасет.

### M09. Настоящая модель и полная цепочка качества не проверены — P1 для LLM-демо · N · известно ранее

**Доказательство:** [integration-verification.json](../../eval/runs/2026-10-19-branch-integration/integration-verification.json) явно фиксирует отключённые провайдеры; свежие тесты этого аудита также выполнялись без них. Синтетические model responses показывают дефекты защиты, но не измеряют частоту галлюцинаций, качество RU/KK/EN, latency/cost и доступность конкретного model account.

**Лучшее решение:** после устранения детерминированных P1 провести ограниченный реальный прогон выбранного runtime: fixed data/index/prompt/model/config, повторы, p50/p95, tokens/cost, fallback rate, human-калибровка faithfulness и языков. Доступ к моделям и параметрам проверять именно выбранным аккаунтом. Не менять модель вслепую по её названию.

**Приёмка:** provenance-bound live report для UI→API→активный retrieval→настоящая модель→карточки; отдельные оценки текстов и constraints, с сохранением ошибок и NOT_EVALUATED. Шаблонный профиль может демонстрироваться отдельно с честной маркировкой.

## 5. Данные, сбор и происхождение фактов

### D01. Частичный сбор может заменить пригодный snapshot резко усечённым — P1 · R

**Доказательство:** [run_pipeline.py](../../data/run_pipeline.py), 199–214. В изолированной пересборке OSM вернул один POI, Overture — unavailable без кэша. Предыдущий набор **3** заменён набором **1**, итог `status=partial`. Исходные production-файлы не менялись.

**Причина:** публикация блокируется только при полностью пустом результате. Статус partial не проверяет обязательность источников, потерянные source ID или аномальное падение покрытия.

**Лучшее решение:** staging snapshot, сравнение с published версией, quality gates по обязательным источникам, количеству/категориям и сохранности ID. Неполный результат сохранять отдельно для review; намеренные изменения состава источников проводить по явной политике.

**Приёмка:** сценарий 3→1 и недоступность обязательного источника не меняют published snapshot; причина отклонения остаётся в отчёте.

### D02. Несколько экспортов не образуют атомарный data bundle — P1 при обновлении действующего набора · R

**Доказательство:** [run_pipeline.py](../../data/run_pipeline.py), 30–34, 211–220. `write_json` атомарен для одного файла, но файлы меняются последовательно. Инъекция `OSError` на `pois_leisure.json` оставила **новый pois.json**, **старый manifest** и **старый leisure**.

**Лучшее решение:** immutable каталог версии с полным bundle и хешами; после всех проверок атомарно переключать один `current`/manifest pointer. Runtime загружает всю версию через него. Этот подход также упрощает D01 и I11.

**Приёмка:** сбой на любой стадии оставляет читателю полностью старую либо полностью новую версию; каждый manifest содержит реальные hashes всех её артефактов.

### D03. Сборщик событий может выбрать случайный филиал сети — P2 · R

**Доказательство:** [events.py](../ayat_backend/pipeline/events.py), 148–169. Synthetic future event с `venue='Coffee BOOM'`, без coordinates, и два реальных legacy POI: изменение порядка `osm:n10170946742` / `osm:n10295608316` меняет выбранный филиал. Исходные venue/coordinates заменяются, evidence сопоставления не сохраняется. В legacy snapshot **124** неоднозначных имени у **431** POI: это область риска, не число доказанно неправильных событий.

**Причина:** выбирается первый максимальный `token_set_ratio>=88` по всему городу без проверки уникальности/отрыва кандидата, адреса и филиала.

**Лучшее решение:** identity/address/coordinates перед fuzzy name; ambiguous event оставлять unresolved в очереди review. Сохранять `source_venue`, исходные coordinates, candidates/scores, метод и версию matcher.

**Приёмка:** перестановка POI не меняет match; общее имя сети без филиала не создаёт `poi_id`; исходное evidence сохраняется.

**Текущий объём:** из **140** исходных событий **71** имеют legacy POI-связь, **69** не имеют. Исправленный Ayat remap безопасно активирует **60**, исключает **80** unmatched; это уже исправленная совместимость, а не доказательство качества исходного fuzzy-link каждого события. Для полноценного event-сценария нужно восстановить недостающие связи по доказательствам, не назначать их принудительно.

### D04. Часы ошибочно атрибутированы OSM у 33 активных POI — P2 · R

**Доказательство:** [hours.py](../ayat_backend/app/hours.py), 95; [i18n.py](../ayat_backend/app/i18n.py), 14; [team_data.py](../ayat_backend/app/team_data.py), 101, 116; [normalize.py](../../data/collect/normalize.py), 221–226. У **380** активных POI с часами: 9 CityPass, 23 Dodo, 348 nominal OSM. Общий suffix всегда пишет «данные OSM»: прямых неверных атрибуций **32**. Например, `citypass:120` получает «Открыто до 18:00 (данные OSM)».

Дополнительно Байтерек `osm:way/230401645` получил часы только из `citypass:57`, но адаптер ставит источником часов primary source сущности — OSM. Вместе **33** неверные атрибуции.

**Лучшее решение:** field-level provenance для расписания: source ID/URL, acquired/source updated/check dates, conflicts; label формируется из происхождения именно поля. Не подменять источник поля источником всей сущности.

**Приёмка:** все 33 записи показывают верный источник; у Байтерека указан CityPass; unknown source не превращается в OSM.

### D05. Подтверждённых содержательных фактов мало для обещанных сценариев — P2 · S · частично известно ранее

Свежий пересчёт [canonical JSON](../../data/processed/pois.json), [stats](../../data/processed/stats.json) и активного Ayat view:

| Показатель | Все canonical | Досуг canonical | Активный Ayat |
|---|---:|---:|---:|
| POI | 14 006 | 2 759 | 2 751 |
| Исходное описание | 269 | 37 | 37 |
| Структурированный шаблон | 13 737 | 2 722 | 2 714 |
| Часы | 2 083 | 388 | 380 |
| Wheelchair | 305 | 68 | 66 |
| Имя KK | 709 | 76 | 76 |
| Имя EN | 898 | 159 | 158 |
| Явный kid_friendly=true | 3 | 3 | 3 |
| source_classification_unverified | 8 473 | 1 794 | 1 788 |

У **657 canonical кафе** только **одно** исходное описание. **11 247** POI имеют категорию `other`: в Ayat это ориентиры, а не досуговые рекомендации. В активном view часы неизвестны у **2 371/2 751**, исходное описание есть лишь у **37/2 751**. Наличие шаблона не подтверждает тишину, розетки, интерактивность, безопасность или доступность. Посетительских рейтингов в canonical нет; отсутствие рейтингов нельзя заполнять придуманной оценкой.

**Лучшее решение:** curator backlog по пяти ключевым сценариям: ограниченная полезная выборка с подтверждёнными часами, входом, Wi-Fi, детскими возможностями и языковыми именами. Разделять confirmed/false/unknown/conflicting; хранить evidence. Не наращивать показатель заполненности шаблонами.

**Приёмка:** измеряется доля рекомендаций, реально удовлетворяющих фактическому требованию с источником; unknown остаётся unknown. Целевые требования качества задаются по сценариям, а не только по общему количеству POI.

### D06. Непроверенная классификация остаётся в активных рекомендациях — P2 · S

**Доказательство:** [overture.py](../../data/collect/overture.py), 132–142; [team_data.py](../ayat_backend/app/team_data.py), 173–180. Из активных POI **1 788** имеют `source_classification_unverified`. Пример: `overture:f1816ce2-7a42-4046-94a4-92a431579c73`, «Северный Казахстан, Казахстан», категория park, остаётся активным. Специальное исключение реализовано только для трёх unverified playground.

**Лучшее решение:** review подозрительных имён/категорий и отдельная eligibility-политика для высокой неопределённости; classification-only признак не превращать в подтверждённую пригодность. Массово удалять все 1 788 записей без проверки нельзя: флаг означает отсутствие верификации, а не доказанную ошибку.

**Приёмка:** подозрительный объект не предлагается как проверенный парк без evidence; разрешённые классификации и уровень доверия видны в diagnostics и evaluation.

### D07. Даты экспорта не подтверждают актуальность работы и часов — P2 · S

**Доказательство:** [normalize.py](../../data/collect/normalize.py), 90–94, 115–116, 316; [source_manifest](../../data/processed/source_manifest.json). У **6 086/14 607** source records нет `source_updated_at`; среди дат источников есть записи 2012–2018 годов. Top-level `updated_at/collected_at` обновляется днём нормализации, а реальные даты сохранены отдельно. Во всём canonical неизвестны часы **11 923** POI.

Все существующие **2 083** строки часов успешно разбираются установленным parser: это проблема покрытия/достоверности, не массовая синтаксическая ошибка. Дата сборки 19 октября не означает онлайн-проверку всех заведений.

**Лучшее решение:** различать `built_at`, `acquired_at`, `source_updated_at`, `checked_at`; freshness budget для критичных полей и очередь обновления. Просроченность понижает confidence, conflicts рассматриваются отдельно. Для demo вручную проверить небольшой сценарный набор.

**Приёмка:** свежая пересборка старого кэша не делает часы «свежепроверенными»; API/карточки показывают верную дату и уровень подтверждения.

### D08. У части текстов не установлены условия повторного использования — P2 · S/N

**Доказательство:** в source records **69** значений `license=not_specified`; **18** активных исходных описаний получены с сайтов. [source_manifest](../../data/processed/source_manifest.json) честно не заявляет общую открытую лицензию; [web_sources.py](../../data/collect/web_sources.py), 736, сохраняет соответствующее ограничение.

Это установленный пробел в подтверждении provenance/условий использования, а не вывод о юридическом нарушении. Наличие source URL само по себе не устанавливает разрешение на любое копирование текста.

**Лучшее решение:** сверить условия конкретных источников/выдержек, сохранять атрибуцию на уровне текста; для источников без установленных условий ограничить публикуемый материал проверенными фактами и допустимым форматом после соответствующей проверки. Не распространять одну blanket license на смешанный bundle.

**Приёмка:** для публикуемых descriptions известны source, условия использования и требуемая атрибуция либо текст исключён из распространения до проверки.

### D09. Остались кандидаты в дубли, требующие ручного решения — P3 · R

**Доказательство:** повторный расчёт на текущем canonical и [duplicate_review.json](audits/2026-10-19-data/duplicate_review.json), 15–34: **52 пары** с одинаковым нормализованным primary name и расстоянием <50 м; **51** нерешённая и **1** пара разных сущностей tenant/host. Прежние **53** относились к набору до объединения Book Cafe.

**Лучшее решение:** review queue по contact/address/source evidence; отдельно tenant/building и сети/филиалы. Решения versioned и воспроизводимые, все source ID сохраняются. Не ослаблять глобальный matcher ради уменьшения числа записей.

**Приёмка:** у каждой пары есть merge/keep/unresolved с причиной; подтверждённые разные сущности не склеиваются; нерешённые не считаются доказанными дублями.

### D10. Пешеходный граф покрывает не весь активный набор и не доказывает доступность пути — P2 · R/S

**Доказательство:** [geo.py](../ayat_backend/app/geo.py), 103–117; [graph.py](../ayat_backend/pipeline/graph.py), 16–18. Граф: **42 455** узлов, **122 036** направленных рёбер; bbox в порядке lon/lat `[71.330021,51.0800416,71.5199954,51.1999998]`. Из 2 751 активных POI **98** вне bbox, **2 653** внутри; у одной точки внутри nearest-node snap >250 м. Fallback уже предусмотрен — отсутствие graph path само по себе не является падением.

**Лучшее решение:** показывать network/fallback и uncertainty; проверять snap, компоненты связности, входы и мосты на сценарном наборе. Для важных deadline не трактовать эвристическое время пешком/на машине как гарантированное. Произвольное расширение bbox не заменяет проверку маршрутизируемой сети.

**Приёмка:** UI и API различают подтверждённую сетевую геометрию и оценку; не возвращают network-label для фактического fallback; выбранные demo routes проверены по реальному доступному пути. Исправление B09 обязательно даже внутри покрытия.

Предпочтительная архитектура для этого объёма — общие детерминированные библиотеки и согласованные артефакты: `Snapshot/Eligibility → CandidateFacts → TemporalPlan → TextGeneration → FinalSemanticValidation`. Полная миграция на микросервисы или одновременная перепись обоих backend для этих исправлений не нужна.

Не следует считать решением: ослабление красного теста readiness; подключение старой матрицы embeddings без проверки соответствия; подбор случайного филиала для снятия ambiguity; выдумывание часов/рейтингов/удобств; перенос старых метрик Ayat на canonical UI. Эти действия скрывают недоказанность вместо устранения причины.
